Vibe Coding: from an HTML file to an Android APK

For non-coders. You describe the app in your own language. A Claude Code cloud session, embedded with a GitHub repository, writes the files. GitHub builds the APK.

Vibe coding means you judge the running app, and the model writes the program. Andrej Karpathy gave the practice that name on 2 February 2025. This manual is the version you can ship: every change is a GitHub commit, every installable file is built by a recorded run, and you can say, in plain language, what the app is allowed to do.

You stay in a browser, and you install the result on an Android phone. The product that does the writing is Claude Code in the cloud, at claude.ai/code. The ordinary Claude chat page can draft HTML. It does not clone your repository, push a branch, or leave you a build you can re-run. Use the cloud session.

1. The path

  1. You create an empty GitHub repository.
  2. You open a cloud session with that repository already selected. That selection is the embedding.
  3. You describe the screen in the language you speak. Claude writes www/index.html and the files next to it.
  4. In the same session, Claude wraps those files with Capacitor 8. Capacitor makes an Android app whose only screen is your HTML.
  5. Claude adds a GitHub Actions workflow. GitHub’s build machine has the Android SDK. The session’s machine does not.
  6. You download app-debug.apk and install it.
  7. Each later change is a new message, a new branch, and a new APK.
  8. When the app is worth keeping, you sign it with one key you store yourself. A version tag produces app-release.apk (install on a phone) and app-release.aab (upload to Google Play).

2. Accounts and the GitHub connection

You need a GitHub account, a Claude subscription that includes cloud sessions, a browser, and an Android phone. Cloud sessions are included on Pro, Max, and Team plans, and on Enterprise seats that include Claude Code. The session counts against that plan’s usage. There is no separate charge for the virtual machine. Signing in with an API key does not start a cloud session.

Create the repository

  1. On GitHub, choose New repository.
  2. Name it with letters, numbers, and hyphens, for example errand-list.
  3. Choose Private or Public. A private repository works after the Claude GitHub App is installed on it.
  4. Check Add a README file. The session needs a branch to clone. Leave the license and the ignore template empty.
  5. Create the repository. The address is https://github.com/OWNER/REPO. You will type OWNER/REPO.

Connect Claude Code to GitHub

  1. Open https://claude.ai/code.
  2. Choose Sign in with GitHub and approve the request. GitHub sends you back to claude.ai/code.
  3. For a private repository, install the Claude GitHub App on the account or organization that owns it, and include this repository. An organization owner may have to approve the install. The install also turns on Auto-fix for pull requests in that repository.
  4. On Pro and Max, onboarding creates an environment named Default with Trusted network access. On Team and Enterprise, leave the prefilled name and network access as they are and choose Create & finish. If the page says GitHub access is required, an Owner first turns on the GitHub connector at Organization settings → Connectors, then you reload.

Default is the right environment for this manual. Trusted access reaches GitHub, npm, Maven, and Gradle. It does not include dl.google.com, which is where Android SDK packages are downloaded. That is why section 6 builds the APK on GitHub Actions, where the SDK is already installed. Section 13 is the optional path that adds dl.google.com and builds inside the session.

Organizations with Zero Data Retention, the HIPAA configuration, or customer-managed encryption keys cannot start these cloud sessions. If the page says cloud sessions are unavailable, that setting is the reason.

The same connection from a terminal

Use this only if you already use the gh command. In a shell: gh auth login, then gh auth refresh -s workflow. Open the Claude Code CLI, run /login with the same claude.ai account, then run /web-setup and confirm. The workflow scope is what allows a later push of .github/workflows. On Team and Enterprise, /web-setup appears after an Owner turns on Quick setup. Disconnecting GitHub at claude.ai/customize/connectors removes the token from cloud sessions. Your local gh login stays until you revoke it on GitHub.

3. Embed the repository in a session

A cloud session runs on an Anthropic-managed virtual machine: Ubuntu 24.04, x86_64, about 4 vCPUs, 16 GB of RAM, and 30 GB of disk. It clones the repository you selected. You do not get a shell. You type what you want, and Claude runs the commands. Closing the browser tab leaves the session running. After a few minutes with no messages, the machine pauses. Open the session again from the sidebar. If the page says the environment expired, the conversation is restored on a new machine; a command that was still running is not restored.

From the browser or the phone

  1. Open claude.ai/code, or the Code tab in the Claude mobile app.
  2. Under the message box, open the repository selector and choose OWNER/REPO. Add no second repository. A session with one repository loads CLAUDE.md and the repo’s Claude settings. A session with several repositories does not load hooks from .claude/settings.json.
  3. Leave the branch on the default branch for the first session. Claude will create html-app. For a later session that must continue unmerged work, change the branch in the control next to the repository.
  4. Set the permission mode. Plan: Claude proposes the approach and waits. Accept edits: Claude edits files and pushes. Auto: a classifier reviews actions when your plan allows it. Cloud sessions have no Manual mode and no Bypass mode.
  5. Paste the message. Press Enter.

Start message 1 in Plan. When the plan matches the message, reply Approved. Build it and push the branch. Switch the mode to Accept edits before message 2.

4. How to write a message

  1. One change per message.
  2. Name the visible result: what a person sees, what a tap does, what is still there after the app closes.
  3. Name the file when you know it.
  4. State what must stay: the app id, the signing setup, and the screens you did not mention.
  5. When something fails, paste the error unchanged. Add one sentence: what you expected on the phone.
  6. End with: commit, push the branch, leave main unchanged.
  7. Read the diff by behavior. You are checking that the words you asked for are present, that appId is yours, and that no .jks file appears.

The diff view shows a count such as +42 −18. Open it. Select a line, type the correction, and press Enter. The comment waits. Your next message sends it with the rest of the instruction, including the file and line. When the diff is right, choose Create PR at the top of the diff view and open a full pull request. Use that button. Inside this session, gh pr create calls GitHub GraphQL, and the session proxy answers GitHub GraphQL is not available from Claude Code sessions.

File: .github/workflows/android-apk.yml

name: Android APK

on:
  pull_request:
  push:
    branches: [main]
    tags: ["v*"]
  workflow_dispatch:

jobs:
  build:
    runs-on: ubuntu-24.04
    permissions:
      contents: write
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: "22"
          cache: npm

      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: "21"

      - name: Copy HTML into the Android project
        run: |
          npm ci
          npx cap sync android
          chmod +x android/gradlew

      - name: Install Android SDK 36
        run: |
          SDK="${ANDROID_SDK_ROOT:-$ANDROID_HOME}"
          SM=$(find "$SDK/cmdline-tools" -name sdkmanager \
            -type f | sort | tail -n 1)
          yes | "$SM" --sdk_root="$SDK" --licenses \
            >/dev/null || true
          "$SM" --sdk_root="$SDK" \
            "platforms;android-36" "build-tools;36.0.0"

      - name: Debug APK
        if: ${{ !startsWith(github.ref, 'refs/tags/v') }}
        working-directory: android
        run: ./gradlew assembleDebug --no-daemon

      - name: Upload debug APK
        if: ${{ !startsWith(github.ref, 'refs/tags/v') }}
        uses: actions/upload-artifact@v4
        with:
          name: app-debug
          path: android/app/build/outputs/apk/debug/app-debug.apk
          if-no-files-found: error
          retention-days: 30

      - name: Decode the release keystore
        if: ${{ startsWith(github.ref, 'refs/tags/v') }}
        env:
          ANDROID_KEYSTORE_BASE64: ${{ secrets.ANDROID_KEYSTORE_BASE64 }}
        run: |
          if [ -z "$ANDROID_KEYSTORE_BASE64" ]; then
            echo "Missing secret ANDROID_KEYSTORE_BASE64"
            exit 1
          fi
          echo "$ANDROID_KEYSTORE_BASE64" \
            | base64 -d > "$RUNNER_TEMP/upload.jks"

      - name: Release APK and AAB
        if: ${{ startsWith(github.ref, 'refs/tags/v') }}
        working-directory: android
        env:
          ANDROID_KEYSTORE_FILE: ${{ runner.temp }}/upload.jks
          ANDROID_KEYSTORE_PASSWORD: ${{ secrets.ANDROID_KEYSTORE_PASSWORD }}
          ANDROID_KEY_ALIAS: ${{ secrets.ANDROID_KEY_ALIAS }}
          ANDROID_KEY_PASSWORD: ${{ secrets.ANDROID_KEY_PASSWORD }}
        run: ./gradlew assembleRelease bundleRelease --no-daemon

      - name: Verify the release signature
        if: ${{ startsWith(github.ref, 'refs/tags/v') }}
        run: |
          SDK="${ANDROID_SDK_ROOT:-$ANDROID_HOME}"
          APKSIGNER=$(find "$SDK/build-tools" -name apksigner \
            -type f | sort | tail -n 1)
          "$APKSIGNER" verify --print-certs \
            android/app/build/outputs/apk/release/app-release.apk

      - name: Attach files to the GitHub Release
        if: ${{ startsWith(github.ref, 'refs/tags/v') }}
        env:
          GH_TOKEN: ${{ github.token }}
        run: |
          gh release upload "$GITHUB_REF_NAME" \
            android/app/build/outputs/apk/release/app-release.apk \
            android/app/build/outputs/bundle/release/app-release.aab \
            --clobber

      - name: Upload release files
        if: ${{ startsWith(github.ref, 'refs/tags/v') }}
        uses: actions/upload-artifact@v4
        with:
          name: app-release
          path: |
            android/app/build/outputs/apk/release/app-release.apk
            android/app/build/outputs/bundle/release/app-release.aab
          if-no-files-found: error
          retention-days: 30

The runner is pinned to ubuntu-24.04 because the ubuntu-latest label moves to Ubuntu 26.04 in November 2026. Both images can build this project. The pin keeps the run on the image this file was written for. The SDK step installs platform 36 and build-tools 36.0.0, which match Capacitor 8.

Replacement inside android/app/build.gradle

    signingConfigs {
        release {
            def keystorePath = System.getenv("ANDROID_KEYSTORE_FILE")
            if (keystorePath) {
                storeFile file(keystorePath)
                storePassword System.getenv("ANDROID_KEYSTORE_PASSWORD")
                keyAlias System.getenv("ANDROID_KEY_ALIAS")
                keyPassword System.getenv("ANDROID_KEY_PASSWORD")
            }
        }
    }
    buildTypes {
        release {
            if (System.getenv("ANDROID_KEYSTORE_FILE")) {
                signingConfig signingConfigs.release
            }
            minifyEnabled false
            proguardFiles getDefaultProguardFile('proguard-android.txt'), 'proguard-rules.pro'
        }
    }

signingConfigs must sit above buildTypes, still inside the existing android { } block. A debug build leaves ANDROID_KEYSTORE_FILE empty, so Gradle uses its debug signature. A tag build sets the variable, so Gradle signs app-release.apk and app-release.aab with your key. minifyEnabled false leaves the WebView app uncompressed by R8. Turn that on only when you have a failing release that needs it, and expect a separate round of keep-rules.

10. The signing key

Android installs an update only when the new file is signed with the same key as the installed app and versionCode is higher. The debug APK from Actions uses a new debug key every run. A key you create once, and store, is the key for every later sideload update.

Create it on a computer you control. Java’s keytool is enough. OpenJDK 21 is what this project builds with.

Create upload.jks — run outside the repository folder

keytool -genkeypair -v \
  -keystore upload.jks \
  -storetype JKS \
  -alias upload \
  -keyalg RSA \
  -keysize 2048 \
  -validity 10000

Type a long password. When keytool asks for the key password, press Enter so the key uses the same password. Fill in the name it asks for. Validity of 10000 days from October 2026 ends in 2054, which is after the 22 October 2033 date Android requires of a release certificate.

Copy upload.jks to two places that are not the git repository: a password manager’s file storage, and a second disk. A lost key means every sideload user must uninstall, which deletes the saved list. A new app id produces a second app, not an update.

One-line base64

base64 -w 0 upload.jks
base64 -i upload.jks | tr -d '\n'

The first command is Linux. The second is macOS. The output is one line.

On GitHub: repository → Settings → Secrets and variables → Actions → New repository secret. Create these four. The names must match. Paste the base64 with no quotes and no spaces.

SecretValue
ANDROID_KEYSTORE_BASE64The one-line base64 of upload.jks
ANDROID_KEYSTORE_PASSWORDThe password you typed
ANDROID_KEY_ALIASupload
ANDROID_KEY_PASSWORDThe same password, if you pressed Enter for the key password

Add the secrets after the workflow from section 6 is merged to main. The debug job never reads them. The tag job reads them.

Phone-only fallback, for a personal app: in a cloud session, ask Claude to run the keytool command above with -storepass and -keypass, print the base64, delete upload.jks, and confirm git status does not list it. Copy the base64 into the secret, then delete the session. Deleting a session permanently removes that session’s data. The transcript contained the key until then. For an app other people depend on, create the key on a computer you control.

11. Signed APK and AAB

The cloud session proxy accepts branch pushes and rejects tag pushes. You create the tag in the browser. The tag starts the release half of the workflow.

  1. Confirm main contains the version you want. The on-screen text, versionName, and the tag must be the same number. versionCode must be an integer higher than any build you already installed or uploaded.
  2. On the repository, open Releases → Draft a new release.
  3. In the tag box, type v1.0.0 and choose Create new tag on main.
  4. Title it v1.0.0. Publish the release.
  5. Wait for the Android APK workflow on that tag. Refresh the release page. Download app-release.apk and app-release.aab. If the release page has no files and the workflow is green, download the app-release artifact from the run. Artifacts are deleted after 30 days. Keep the APK and AAB you ship.
  6. The verify step prints the certificate. The alias in that printout is upload.

Uninstall the debug app first. Its signature is different, and Android will refuse the release APK until the debug copy is gone. Install app-release.apk. Add a list item. Then ship v1.0.1 with versionCode increased by 1, and install that APK over the top. The list item must still be there. That test is the proof the key and the version rules are right.

Keep the APK for sideload. Keep the AAB for Play. Play will not accept the APK as a new app’s package.

12. Google Play

New apps enroll in Play App Signing. You upload an AAB signed with your upload key. Google signs the APKs that Play delivers, with a key Google holds. If you lose the upload key, Play can reset it. People who installed from Play keep receiving updates. People who installed your sideload APK do not: the sideload file is signed with the upload key, and the Play file is signed with Google’s key. Those two installs do not replace each other. Uninstall one before installing the other.

Leave Google as the holder of the app signing key. That is the default when you create the app.

  1. Open https://play.google.com/console and create the developer account. Pay the one-time fee shown on that page.
  2. Create the app. The package name must equal appId character for character.
  3. Complete the dashboard tasks the console lists: store listing, the screenshots in the sizes the form names, app access, ads declaration, content rating, target audience, and data safety.
  4. For this errand list, data safety is: the list stays on the device in WebView storage, and the app sends no account and no list contents anywhere. Answer the form to match the code. If the form asks for a privacy-policy URL, ask Claude to write docs/privacy.html that says the same thing, merge it, then in the repository open Settings → Pages → branch main → folder /docs. 13. Building on the session machine

Use this when you want the APK before a pull request exists. The reliable build remains section 6.

At claude.ai/code, create an environment named android-build. Set network access to Custom, include the default domain list, and add one domain: dl.google.com. Set two variables:

BASH_DEFAULT_TIMEOUT_MS=600000
BASH_MAX_TIMEOUT_MS=1800000

Those are 10 minutes and 30 minutes. The defaults are shorter: Claude waits 2 minutes for a foreground command and can ask for up to 10, then the command can continue in the background for up to 30 minutes. A first Gradle build often needs the longer window.

Do not put the SDK install in the environment’s setup script. A setup script is cached only when it finishes in about five minutes. The SDK download is larger than that budget. A script that exceeds it is not cached, and a script that exits non-zero blocks the session from starting.

Message — build here, then push the APK

Install the Android SDK into /opt/android-sdk:
command-line tools, platforms;android-36, and build-tools;36.0.0.
Download the tools from dl.google.com.
Set ANDROID_HOME and ANDROID_SDK_ROOT to /opt/android-sdk.
Run npx cap sync android.
Run android/gradlew assembleDebug --no-daemon.
Copy the APK to releases/app-debug.apk.
Commit only that APK and push this branch.
Do not commit a keystore.

Download releases/app-debug.apk from the branch on GitHub. There is no file browser on the session machine. A file leaves the session by a git push, or it does not leave.

The machine has about 16 GB of RAM and 30 GB of disk. If the build is killed, use the Actions workflow. Packages installed during a session are not there in the next session. The environment cache stores what a setup script installed, and this manual keeps the SDK out of that script on purpose.

16. Before anyone else installs it

  1. You installed this exact APK or Play build on your own phone and used every control.
  2. The version on the screen matches versionName and, for a release, the git tag.
  3. appId is the final id. Changing it later creates a different app.
  4. You asked for this list and you accept it: “List every Android permission and every network host this app uses, in plain language, and point to the file for each.”
  5. An errand list that asks for SMS, contacts, accessibility, or device-admin is the wrong APK. Send a message to remove that permission and build again.
  6. The signing key has two copies outside GitHub. git status does not list upload.jks.
  7. The release you hand to someone is app-release.apk from the tag, or the Play listing. A debug APK from a pull request is for you.

You are responsible for what the APK does on someone else’s phone. You can meet that duty without reading Java: the behavior is on your phone, the permissions are in the list, and the bytes are the artifact from the tag you published.
